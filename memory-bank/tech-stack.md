# 爆弹迷宫 技术栈选型 / Blast Maze Tech Stack Decision

## 1. 文档目标

本文件用于明确《爆弹迷宫》项目的技术选型结论，确保后续工程实施、目录设计、CI、资源流程与发布流程都围绕同一套技术前提展开。

本文件与其他文档的关系如下：

- [game-design-document.md](/Users/tony/src/bomberman/memory-bank/game-design-document.md)
  - 定义玩法、内容结构、地图规则、敌人和道具系统
- [implementation-plan.md](/Users/tony/src/bomberman/memory-bank/implementation-plan.md)
  - 定义实施顺序、里程碑、测试计划和交付路径
- `tech-stack.md`
  - 定义用什么语言、框架、构建工具和资源工作流去实现这些内容

## 2. 选型目标

本项目的技术选型要满足以下优先级：

1. `Windows Build` 优先，能尽快稳定输出桌面包
2. 适合 2D、tile-based、关卡驱动的动作迷宫游戏
3. 代码控制力强，便于精确实现炸弹、碰撞、连锁爆炸和敌人行为
4. 框架足够流行，社区和资料不至于过于稀缺
5. 后续扩展到更多关卡、更多敌人、更多平台时不需要推翻重做

## 3. 最终推荐结论

### 3.1 主结论

本项目推荐技术栈为：

- 主语言：`Rust`
- 主游戏框架：`Bevy`
- Tile 地图方案：`bevy_ecs_tilemap`
- 关卡制作工具：`LDtk` 优先，`Tiled` 作为备选
- UI：Bevy 原生 UI
- 音频：Bevy 原生音频系统
- 构建工具：`cargo`
- Windows 构建目标：`x86_64-pc-windows-msvc`
- 发布形式：`exe + assets` 便携 zip 包

### 3.2 为什么是这个组合

这个组合最符合当前项目目标：

- 我们要做的是规则清晰、tile 逻辑稳定的 2D 单机桌面游戏
- 你当前明确偏好“代码控制优先”
- Windows 是第一优先平台
- Rust 能提供较强的工程约束和长期可维护性
- Bevy 是当前 Rust 游戏开发里最主流、最活跃的通用游戏框架之一
- `bevy_ecs_tilemap` 能很好覆盖本项目最核心的 tile 地图需求

这意味着项目可以围绕“清晰规则 + 强代码控制 + 可持续扩展”的路线推进，而不是被早期编辑器流程或脚本便利性锁死。

## 4. 主栈详细说明

### 4.1 编程语言：Rust

选择 Rust 的原因：

- 编译型语言，适合稳定输出 Windows 可执行文件
- 类型系统和所有权模型有利于控制复杂规则系统的边界
- 对炸弹生命周期、敌人状态、关卡状态机、资源加载等逻辑更容易保持清晰
- 更适合长期维护而不是一次性原型

选择 Rust 的代价：

- 学习曲线比 C# 更陡
- 初次工程搭建成本高于脚本型方案
- 编译时间和调试体验通常不如编辑器驱动型工作流直接

结论：

- 考虑到本项目规则复杂度、长期扩展和你偏好的“代码控制优先”，Rust 是合理主语言。

### 4.2 游戏框架：Bevy

选择 Bevy 的原因：

- 在 Rust 游戏框架中足够流行、社区活跃、资料较多
- 适合 2D 游戏和 ECS 驱动的实体系统
- 对玩家、敌人、炸弹、爆炸、道具这类多实体交互结构非常自然
- 与 Rust 工具链衔接直接，Windows 构建流程清晰
- 后续扩展 UI、音频、状态管理、内容驱动时不需要切框架

选择 Bevy 的代价：

- API 在活跃发展中，升级时需要关注版本迁移
- 编辑器生态不如 Godot、Unity 完整
- 对团队的工程化要求高于可视化引擎工作流

结论：

- 在“Rust + 代码控制优先 + Windows 优先”的前提下，Bevy 是最佳主框架。

### 4.3 Tile 地图：bevy_ecs_tilemap

选择原因：

- 本项目本质上是标准 tile-based 迷宫动作游戏
- 爆炸传播、墙体阻挡、敌人寻路压力都强依赖稳定的 tile 表达
- `bevy_ecs_tilemap` 能让地图渲染和逻辑层更清晰地围绕格子展开

要求：

- 地图逻辑必须以 tile 数据为唯一真实来源
- 视觉表现可以平滑，但不能反向决定规则判定

### 4.4 关卡工作流：LDtk 优先，Tiled 备选

推荐优先使用 `LDtk`：

- 对 2D tile 地图、关卡分层和实体标注更友好
- 更适合作者控制模板 + 可配置内容的工作流
- 便于管理主线关卡、奖励关和地图元数据

保留 `Tiled` 作为备选：

- 如果团队对 Tiled 更熟悉，可先用 Tiled 打通最小闭环
- 但主目标仍然是形成结构化、可扩展的关卡数据流程

结论：

- 正式路线优先 `LDtk`
- 若原型期为赶进度，可以允许 `Tiled` 作为过渡方案

## 5. Windows Build 方案

### 5.1 本地开发环境

Windows 开发环境要求：

- Rust stable toolchain
- Visual Studio Build Tools
- Windows SDK
- Git

本地核心命令：

- 开发运行：`cargo run`
- 发布构建：`cargo build --release`

### 5.2 CI 方案

CI 推荐：

- GitHub Actions
- `windows-latest` runner

CI 目标：

- 每次主分支或开发分支提交都验证 Windows 可构建
- Release 构建输出版本化 artifact
- 为后续 zip 分发做自动化准备

### 5.3 首阶段发布形式

首阶段不追求安装器，而是追求“稳定可跑”：

- 交付物为一个 zip 包
- zip 包内包含：
  - `BlastMaze.exe`
  - `assets/`
  - 运行说明

首阶段明确不做：

- 安装器
- 自动更新器
- 代码签名体系
- 商业化分发集成

## 6. 为什么不选其他主方案

### 6.1 为什么不选 Godot 4.5 + C#

Godot 的优点：

- Windows 导出很成熟
- 2D 工具链完整
- 编辑器体验优秀
- 开发迭代速度快

但不作为当前主栈的原因：

- 你当前偏好不是“编辑器优先”，而是“代码控制优先”
- 本项目的核心难点是规则精度，而不是复杂场景编辑
- 若过早依赖编辑器主导工作流，后续在某些规则层面可能不如纯代码架构直观

结论：

- Godot 是最强备选之一，但不是这轮推荐主栈。

### 6.2 为什么不选 MonoGame + C#

MonoGame 的优点：

- 代码控制力强
- C# 工具链成熟
- Windows 目标天然友好

但不作为当前主栈的原因：

- 相比 Bevy，需要自己补更多现代 2D 工作流能力
- 地图、资源、工具和系统层组织需要手工搭建更多基础设施
- 在保持代码控制的同时，Bevy 在系统组织和扩展空间上更合适

结论：

- MonoGame 是可行备选，但综合效率不如 `Rust + Bevy`。

### 6.3 为什么不选 Unity 6 + C#

Unity 的优点：

- 行业通用
- 工具成熟
- Windows Build 流程成熟

但不作为当前主栈的原因：

- 引擎更重
- 当前项目规模不需要如此大的编辑器和生态负担
- 你当前明确偏向代码控制，而不是完整编辑器生产线

结论：

- Unity 可做，但与当前目标并不最匹配。

## 7. 技术约束与边界

后续实现必须遵守以下边界：

- 所有关键玩法规则必须由代码和数据定义，不得依赖编辑器隐式行为
- 爆炸传播、敌人行为、碰撞阻挡必须保持确定性
- 地图与关卡内容必须外部数据化
- Windows 构建链必须从项目早期就打通，而不是等临发布再处理
- 若未来要支持多人模式，应作为后续扩展，不得反向污染单人主流程架构

## 8. 风险与应对

### 风险 1：Bevy 版本演进

应对：

- 锁定主版本
- 不在早期频繁升级框架
- 关键系统尽量做薄封装

### 风险 2：Rust 工程上手成本

应对：

- 先建立最小可运行工程模板
- 优先完成 Windows Build 和核心玩法闭环
- 把高阶道具和高阶敌人放到后期接入

### 风险 3：资源工作流分散

应对：

- 尽早统一关卡制作工具
- 明确地图、敌人编排、掉落配置的文件格式
- 不允许地图规则一部分写在代码里、一部分写在编辑器里

## 9. 最终结论

本项目当前唯一推荐技术栈为：

- `Rust + Bevy + bevy_ecs_tilemap + LDtk + cargo + Windows MSVC toolchain`

备选方案保留为参考，但不是当前实施路线：

- `Godot 4.5 + C#/.NET 8`
- `MonoGame + C#`

因此，后续所有工程初始化、目录设计、CI、资源工作流和发布策略，都应围绕这套主栈展开。
